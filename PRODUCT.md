## Platform
android

## Stack
Confirmed: Kotlin, Jetpack Compose Material 3, coroutines, MediaCodec; one app module.

## Users and purpose
Camera owner setting up local access, viewing one V380 live stream, browsing SD recordings, saving video and changing supported camera settings, and controlling supported PTZ on the same Wi-Fi LAN or a direct camera AP connection.

## Capabilities and constraints

Experimental debug talkback sends phone microphone audio only after speaker capability, session-bound metadata, foreground microphone permission and correlated start ACK. PCM100 mono16 at8/16kHz uses raw PCM. The observed codec102/mono16kHz session now follows the vendor microphone PCM21 path with256-byte IMA ADPCM payloads; metadata102 is not treated as an AAC microphone payload. The attempted AAC uplink caused loud squealing with no intelligible speech according to the owner and has been removed. Live provides explicit start/stop; lifecycle changes stop capture without resuming it. Audio remains in bounded volatile buffers and is excluded from storage/diagnostics. The owner reported intelligible microphone audio at the camera speaker through the bounded voice test, so the codec102 PCM21/IMA uplink is treated as owner-verified for that session; no latency, durability or other-firmware claim is made. The vendor-parity microphone front-end (audio focus, communication audio mode, platform echo cancellation) is enabled by default (`-PtalkbackMicFrontendV2=false` disables it). An optional bounded debug probe (`TALKBACK_PROBE_ENABLED`, default off) can send at most 15 silence frames or a 2-second voice test and stops on its own. validation/talkback-fix/results.json records the evidence. Legacy, cloud, other formats and incoming camera audio remain unavailable.

Multiple saved profiles; one foreground stream. The debug build contains experimental Legacy V2 and IoT LAN adapters for discovery, local authentication, video and PTZ, plus manual profile entry and sanitized diagnostics/export. SD/HD and directional PTZ/stop depend on the session state and camera capabilities; controls enable only after video reaches Streaming. MediaCodec renders video to a SurfaceView. Release builds do not enable these experimental adapters.

AP setup separates the camera hotspot, local camera access and home-Wi-Fi credentials. It authenticates the camera before sending Wi-Fi configuration, supports direct AP use, and requires rediscovery of the same device and successful local login before completing home-Wi-Fi setup. The observed fresh new-platform PIN-binding path requires a cloud-issued owner binding token and is not implemented by this LAN client; authenticated LAN password changes are a separate path. Optional password storage uses Android Keystore and is off by default. Indonesian UI and system light/dark theme remain. IoT recording list/playback and single-segment video-only MP4 export are experimental debug features. Camera settings read actual property values and require write readback; supported controls cover orientation, lights and recording. SD status/capacity are readable; format is available under the REA-verified vendor ACK contract (correlated result1000; completion only when status4→1 is observed), while terminal status semantics remain unverified and are never inferred. Legacy recording/settings, audio export, remote/cloud/P2P, grids are deferred. Native tests for these new screens/export compile but could not run because the emulator crashed during boot; camera tests remain deferred.

Experimental debug AP editing is available in camera settings after successful local authentication, explicit SoftAP capability, direct AP network/identity checks and readback. A single write is followed by reconnect and verification; durable nonsecret recovery never replays the write. AP credentials remain separate from camera login and are not persisted. Legacy/unknown profiles remain gated. Native runtime and owner-camera acceptance remain unverified.

Debug0.4.2 extends camera settings with local alarm/motion/sound switches, adding/removing/editing alarm intervals within conservative per-day limits, light sensitivity/schedules, camera version reads, preset save/recall/delete and editing inactive patrol routes. Calibration reports acceptance only and requires the user to check movement; restart uses durable send-once recovery and identity verification, without claiming a reboot from reconnection alone. Patrol start/stop, motion sensitivity, unsupported area mapping variants and per-recording SD delete remain gated or unfinished pending their contracts; SD format is available under the vendor ACK contract. Native UI/storage runtime remains unverified after API35 and fallback API26 emulator boot SIGSEGV with KVM; physical-camera testing is still deferred. See analysis/camera-management-wire.md for current limits.

## Approved Settings UI redesign

A single bottom panel holds light schedules, alarm/motion detection and presets/patrol, each independently expandable with a Build icon and Not working yet label, following the owner's report. This is a presentation classification; it does not change protocol support or claim camera compatibility. Simple subheadings replace nested cards. Errors, progress, unsaved drafts and pending recovery remain visible when closed; opening groups never contacts the camera. Hotspot permissions, inspection and inputs appear when the connection group opens; closing it clears hotspot/local-login passwords and retains the SSID draft. Basic Save appears before the bottom panel while drafts exist. Both languages, themes, accessibility and all existing protocol gates remain. Current validation scope is in validation/settings-simplified/results.json. The earlier nine-card implementation and physical API33 synthetic results in validation/settings-redesign are historical evidence for that source, not validation of this layout.
